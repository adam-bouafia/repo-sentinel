### [low] Preferences allow a 1-second update interval that the extension silently clamps to 2
*other* - new

prefs.js builds the Update Interval SpinRow with `lower: 1`, and the gschema default/range documentation says "Update interval in seconds" with no range enforcement. extension.js then does `const interval = Math.max(2, this._settings.get_int('update-interval'))` when scheduling, so a user who sets 1 gets 2 with no feedback. The emission math in _updateData uses the unclamped `this._settings.get_int('update-interval')` for energyKWh, so at a setting of 1 the energy for the interval is computed with 1s while the loop actually runs every 2s — under-counting emissions by half.

Evidence: prefs.js: `adjustment: new Gtk.Adjustment({ lower: 1, upper: 60, ... })` for 'Update Interval'. extension.js _scheduleNext: `const interval = Math.max(2, this._settings.get_int('update-interval'));`. extension.js _updateData: `const interval = this._settings.get_int('update-interval'); ... const energyKWh = (power.watts * interval / 3600) / 1000;`.

Fix: Set the SpinRow lower bound to 2 (and/or use the same clamped value in _updateData) so the scheduling interval and the energy integration window always agree.

Evidence: data/country_intensity.json is a bare JSON object of 56 country->number entries with no metadata keys. lib/carbon.js: `const COUNTRY_INTENSITY_BUILTIN = { 'US': 388, 'CA': 150, 'FR': 60, ... }` merged under the JSON in loadCountryIntensityMap(). gschema default: `intensity-provider` = 'auto-country'. Fix: Add a source/year field (or a comment block in the README) documenting where the averages come from and when they were last updated, and consider generating lib/carbon.js's fallback table from the JSON to avoid drift.
