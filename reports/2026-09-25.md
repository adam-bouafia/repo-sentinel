### [medium] All GitHub Actions pinned to node20-era majors; Node 20 was removed from runners on 2026-09-23
*ci*

.github/workflows/ci.yml uses actions/checkout@v4 and actions/upload-artifact@v4; .github/workflows/release.yml uses actions/checkout@v4. Both of those majors declare `using: node20` in their action.yml. GitHub removed Node 20 from Actions runners on 2026-09-23 (two days ago); node20 actions are now force-migrated onto Node 24, which is an untested runtime for these versions. Current upstream releases are actions/checkout v7.0.1 (published 2026-07-20) and actions/upload-artifact v7.0.1 (published 2026-04-10) - both three majors ahead and both running natively on Node 24. Runs today still pass, so nothing is broken yet, but the deprecation deadline has already passed and the Release workflow is what publishes to extensions.gnome.org, so a runtime regression here blocks releases.

Evidence: .github/workflows/ci.yml lines: `- uses: actions/checkout@v4`, `- uses: actions/upload-artifact@v4`; .github/workflows/release.yml: `- uses: actions/checkout@v4`. upstream_version(github, actions/checkout) = v7.0.1; upstream_version(github, actions/upload-artifact) = v7.0.1. https://github.blog/changelog/2025-09-19-deprecation-of-node-20-on-github-actions-runners/

Fix: Bump to actions/checkout@v7 and actions/upload-artifact@v7 in both workflow files. upload-artifact v5+ changed default artifact naming/overwrite semantics, so verify the `shell-extension` artifact still uploads as expected before tagging the next release - that is why I am reporting this rather than opening a PR.

### [medium] extension.js: async _updateData() can re-arm timeouts and touch destroyed actors after disable()
*other*

CO2Indicator._updateData() is async and awaits resolveIntensity() (a network round-trip to api.electricitymap.org / ipapi.co with no Gio.Cancellable - lib/carbon.js calls session.send_and_read_async(msg, GLib.PRIORITY_DEFAULT, null, ...)). destroy() removes this._timeoutId and calls clearEphemeralTimeouts(), but it cannot stop an in-flight HTTP request. If the user disables the extension while that request is pending, the continuation resumes afterwards and (a) calls sleepMs(), which registers a brand-new GLib timeout into ephemeralTimeouts *after* clearEphemeralTimeouts() already ran, (b) calls this._updateUI(), which does this._label.set_text() on a destroyed St.Label, and (c) hits the `finally` block, which unconditionally calls this._scheduleNext() and installs a fresh recurring GLib.timeout_add_seconds source. The extension therefore keeps polling /proc and repainting after it has been disabled. Leftover main-loop sources after disable are one of the most common EGO rejection reasons, and this repo's own README checklist calls it out.

Evidence: extension.js: `async _updateData()` -> `const intensityResult = await resolveIntensity({...})` then `await sleepMs(sampleMs)`; `finally { this._updating = false; this._scheduleNext(); }`. destroy(): `if (this._timeoutId) { GLib.source_remove(...) } clearEphemeralTimeouts();`. lib/carbon.js httpGet(): `session.send_and_read_async(msg, GLib.PRIORITY_DEFAULT, null, ...)` - null cancellable.

Fix: Set `this._destroyed = true` at the top of destroy(), bail out early after every `await` in _updateData() and before `this._scheduleNext()` in the finally block, and pass a Gio.Cancellable through httpGet() that destroy() cancels (store it and call cancel() plus reset it in resetSoupCache()).

### [low] prefs.js Data Management buttons are never parented to their rows, so no button is rendered
*other*

In _buildDataManagementGroup(), five Gtk.Buttons (exportTotalsBtn, exportHistoryBtn, exportOverallToggleBtn, exportOverallAllBtn, importOverallBtn) are constructed and passed only as `activatable_widget:` in the Adw.ActionRow constructor - they are never added with add_suffix(). Nothing parents those widgets, so the 'Export'/'Import' labels are not drawn and the rows look inert. Compare _buildHistoryGroup(), which does it correctly: `importRow.add_suffix(importBtn); importRow.set_activatable_widget(importBtn);`. An unparented widget held only through the activatable-widget property is also a GJS lifetime hazard.

Evidence: prefs.js _buildDataManagementGroup(): `group.add(new Adw.ActionRow({ title: 'Export Totals Snapshot (CSV)', subtitle: ..., activatable_widget: exportTotalsBtn }));` (exportTotalsBtn never add_suffix'd) vs prefs.js _buildHistoryGroup(): `importRow.add_suffix(importBtn); importRow.set_activatable_widget(importBtn);`

Fix: For each of the five rows, create the row first, call row.add_suffix(btn) and then row.set_activatable_widget(btn), matching the pattern already used for 'Import/Merge History' and 'Recent History Preview'.
