### [medium] "Enable Periodic Export" timer is destroyed and recreated on every update cycle, so it never fires
*other* - new

In `extension.js` the indicator connects a handler to the *unfiltered* `changed` signal: `this._settingsChangedId = this._settings.connect('changed', () => { this._scheduleNext(true); this._setupPeriodicExport(); });`. `_setupPeriodicExport()` starts with `if (this._periodicExportId) { GLib.source_remove(...) }` and then installs a fresh `GLib.timeout_add_seconds(..., mins * 60, ...)`. Meanwhile every single update cycle writes to GSettings: `updateTotals()` in `lib/storage.js` calls `settings.set_double('daily-total-g', ...)`, `set_double('cumulative-total-g', ...)`, `set_double('weekly-total-g', ...)` and `set_double('monthly-total-g', ...)` unconditionally, and `accumulateSoftwareTotals()` writes `software-totals-json`. Each of those writes re-enters the `changed` handler and restarts the export timer. The export interval is clamped to a minimum of 5 minutes (`Math.max(5, Math.min(240, mins))`) while the update interval is at most 60 seconds (prefs adjustment `upper: 60`), so the N-minute timer is always reset long before it elapses and the periodic CSV export documented in README ("Periodic export: When enabled, the extension exports history every N minutes") never runs. The same handler also needlessly restarts the main update timer on every totals write.

Evidence: extension.js: `this._settingsChangedId = this._settings.connect('changed', () => { this._scheduleNext(true); this._setupPeriodicExport(); });` and `_setupPeriodicExport()` { `if (this._periodicExportId) { GLib.source_remove(...) }` ... `GLib.timeout_add_seconds(GLib.PRIORITY_DEFAULT, mins * 60, ...)` }. lib/storage.js `updateTotals()` calls `settings.set_double('daily-total-g', ...)` etc. on every invocation, and extension.js `_updateData()` calls `updateTotals(this._settings, intervalCO2g, ...)` every cycle.

Fix: Replace the blanket `changed` connection with specific `changed::<key>` handlers for the keys that actually affect scheduling (`update-interval`, `safe-mode`, `enable-periodic-export`, `export-interval-min`), or make `_setupPeriodicExport()` a no-op when the enabled flag and interval are unchanged.

### [low] Daily total rolls over at UTC midnight while weekly/monthly totals use local time, and the displayed reset date can be off by one day
*other* - new

`lib/storage.js` `updateTotals()` computes the day index as `const epochDay = Math.floor(now / 86400000)` from `Date.now()`, i.e. purely UTC. By contrast `getEpochWeek()` builds `new Date(now.getFullYear(), now.getMonth(), now.getDate())` and `getEpochYearMonth()` uses `now.getFullYear()/getMonth()` — both local time. So the "Today" total resets at UTC midnight (e.g. 17:00 local in America/Los_Angeles, 01:00 local in CET) while Week and Month roll at local midnight. Separately, `lib/utils.js` `dateFromEpochDay()` does `const d = new Date(epochDay * 86400000)` (UTC midnight) and then reads `d.getFullYear()/getMonth()/getDate()` (local), so for any negative UTC offset the label shows the previous calendar day. That same function labels the archived history rows in `rollDailyHistory()` (`obj[profile][dateFromEpochDay(prevEpochDay)] = ...`), so exported `co2-daily-history-*.csv` dates inherit the shift.

Evidence: lib/storage.js: `const epochDay = Math.floor(now / 86400000);` vs `const day = new Date(now.getFullYear(), now.getMonth(), now.getDate());` in `getEpochWeek()`. lib/utils.js: `export function dateFromEpochDay(epochDay) { const d = new Date(epochDay * 86400000); const y = d.getFullYear(); ... }`. lib/storage.js `rollDailyHistory()`: `obj[profile][dateFromEpochDay(prevEpochDay)] = settings.get_double('daily-total-g');`

Fix: Derive the day index from local time the same way `getEpochWeek()` does (e.g. `Math.floor(new Date(y, m, d).getTime() / 86400000)`), and format it back with matching local-time construction, so day/week/month all roll over at local midnight.

### [low] Preferences allow a 1-second update interval that the extension clamps to 2, and the energy maths uses the unclamped value
*other* - open since 2026-09-25

`prefs.js` builds the Update Interval spin row with `new Gtk.Adjustment({ lower: 1, upper: 60, ... })`, but `extension.js` `_scheduleNext()` does `const interval = Math.max(2, this._settings.get_int('update-interval'));`. Setting 1 second therefore silently behaves as 2. Worse, `_updateData()` reads the raw setting for the energy conversion — `const interval = this._settings.get_int('update-interval');` then `const energyKWh = (power.watts * interval / 3600) / 1000;` — so at a setting of 1 the timer fires every 2 s but the emission is computed for 1 s, roughly halving accumulated totals.

Evidence: prefs.js: `adjustment: new Gtk.Adjustment({ lower: 1, upper: 60, step_increment: 1, page_increment: 5, value: this._settings.get_int('update-interval') })`. extension.js `_scheduleNext()`: `const interval = Math.max(2, this._settings.get_int('update-interval'));`. extension.js `_updateData()`: `const interval = this._settings.get_int('update-interval');` ... `const energyKWh = (power.watts * interval / 3600) / 1000;`

Fix: Set the adjustment `lower: 2` (and add `<range min="2" max="60"/>` to the `update-interval` key in the gschema), and use the same clamped value for the energy calculation — ideally the actually measured elapsed time between CPU snapshots.

### [info] Bundled country carbon-intensity dataset has no documented source or vintage
*docs* - open since 2026-09-25

`data/country_intensity.json` is a flat map of 56 ISO-3166 codes to integer gCO2/kWh values (e.g. `"FR": 60`, `"PL": 700`, `"ZA": 800`) with no accompanying year, provider or methodology note, and `lib/carbon.js` duplicates a 35-entry subset as `COUNTRY_INTENSITY_BUILTIN` with the same values. Grid intensities move several percent per year, so an undated snapshot silently ages; users of the default "Smart Auto" provider (`intensity-provider` defaults to `'auto-country'`) have no way to judge how current the numbers are. The README only says "Smart Auto uses a bundled country‑average dataset".

Evidence: data/country_intensity.json is a bare object starting `{ "US": 388, "CA": 150, "MX": 430, ... }` with no metadata keys. lib/carbon.js: `const COUNTRY_INTENSITY_BUILTIN = { 'US': 388, 'CA': 150, 'FR': 60, ... };`. schemas gschema.xml: `<key name="intensity-provider" type="s"><default>'auto-country'</default>`.

Fix: Add `"_source"` and `"_year"` keys to data/country_intensity.json (the loader already merges with `{ ...BUILTIN, ...obj }`, so non-numeric keys would need filtering) or document the origin and vintage in the README, and note the refresh cadence.
